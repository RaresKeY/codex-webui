# Context panel capabilities and project boundaries

## Status

Implemented and verified for Outputs, read-only Terminal activity, Side chats, Explorer, and bounded workspace Changes. Browser remains an honest planned surface because the installed public App Server exposes no browser-control contract.

## Source Sync

- Tool registry and related-chat selection: `frontend/src/context-tools.ts` and `frontend/src/context-tools.test.ts`.
- Panel presentation and per-tool state: `frontend/src/App.tsx` and `frontend/src/styles.css`.
- App Server and companion normalization: `frontend/src/api.ts`, `frontend/src/api.test.ts`, `frontend/src/types.ts`, and `frontend/src/app-server-protocol.ts`.
- Thread-scoped terminal projection and bounded Git adapter: `backend/app/main.py`, `backend/app/workspace.py`, `backend/tests/test_api.py`, and `backend/tests/test_workspace.py`.
- Installed protocol authority: schema generated by `tools/generate-app-server-schema.sh` from the official standalone `codex-cli 0.147.0` release.

Changes to a tool's availability, backing, mutation authority, or Project-inheritance claim require this spec and its focused tests to change in the same turn.

## Behavior

The right side is one collapsible contextual panel with a registry-driven selector. A tool is marked available only when its visible data comes from the public App Server or a bounded localhost companion adapter. A planned entry stays non-interactive and says why; the client does not infer private Codex Desktop APIs.

| Tool | Current state | Backing and boundary |
| --- | --- | --- |
| Outputs | Available | Public App Server turn/item notifications and hydrated thread history. Command cards show activity but are not a general shell. |
| Terminal | Available, read-only adapter | Public `thread/backgroundTerminals/list`, scoped to the selected thread. An unloaded companion thread is resumed before retry; a provisional thread or a thread owned by another local writer produces a truthful limited state. No input, spawn, terminate, or clean control is exposed. |
| Side chats | Available, client adapter | Public `thread/list` bootstrap results, ranked by matching workspace and project metadata. Selecting one changes the primary conversation; it does not create an unsupported embedded agent. |
| Explorer | Available, companion adapter | Existing canonical-root-contained workspace tree/read/write routes. It is not Codex Desktop's private Explorer. |
| Changes | Available, companion adapter | Read-only, bounded `git status --porcelain=v1 -z` below the configured workspace. It reports added, modified, and deleted paths; it does not stage, commit, run hooks, or accept arbitrary arguments. |
| Browser | Planned / not supported | The installed ClientRequest schema contains no browser tab, navigation, DOM, or screenshot method. Codex Desktop's in-app Browser is an app UI capability, not a public interface available to this standalone client. |

The installed schema also contains powerful `thread/shellCommand`, `command/exec`, and `process/spawn` families. Their existence does not make an arbitrary Terminal safe for this localhost UI. The companion intentionally projects none of them. Codex-originated commands remain observable through Outputs and the thread-scoped background-terminal inventory.

### Desktop and ChatGPT Project distinction

Three similarly named concepts must not be conflated:

1. A saved local Codex Desktop project groups tasks around a host/path and chooses a local or worktree destination. Live Desktop metadata shows its `projectId` outside App Server, while the resulting local thread receives a concrete `cwd` and writable roots.
2. A projectless Codex task receives a generated Documents/Codex working directory plus projectless-specific app guidance. In the observed local-project and projectless samples, both used the same managed `on-request` approval and workspace-write permission profile; saved project membership did not prevent the Desktop delegation downgrade.
3. A ChatGPT Project is a cloud ChatGPT container for chats, files, and project instructions. Official guidance says project chats use project context and that project instructions override global custom instructions. The separate ChatGPT Work integration can target a cloud `projectId`, while official guidance describes Codex as a separate view with separate workflows and history.

The installed public `ThreadStartParams` accepts `cwd`, sandbox/approval/config, base instructions, developer instructions, and related runtime inputs, but has no Desktop `projectId` field and exposes no method to read Desktop/ChatGPT project membership or project instructions. Consequently this local Web UI can preserve App Server thread state and choose a workspace, but it cannot claim to import or inherit in-app Project settings. Any future instruction import needs an explicit public contract or a user-supplied adapter.

Sources for the cloud distinction: [Projects in ChatGPT](https://help.openai.com/en/articles/10169521-projects-in-chatgpt) and [ChatGPT Work and Codex](https://help.openai.com/en/articles/20001275-chatgpt-work-and-codex).

## Verification

- `backend/tests/test_api.py` covers exact terminal-list forwarding, unloaded-thread resume, provisional-thread limitation, other-session active-writer limitation, and the changes route.
- `backend/tests/test_workspace.py` plus the API's temporary Git-repository test cover canonical containment and actual porcelain parsing without a general command surface.
- `frontend/src/api.test.ts` covers terminal/capability normalization; `frontend/src/context-tools.test.ts` enforces the registry states and related-chat ranking.
- Live on 2026-08-15, the installed App Server returned the documented active-writer conflict for a Desktop-owned thread; the companion converted it to HTTP 200 with an actionable `unavailableReason`. The Changes adapter returned the checkout's real bounded status.
- Desktop and 760-pixel browser checks exercise all selectors, panel collapse, and overlay behavior. Browser remains visibly planned; supported tools render backing-driven empty, limited, or populated states.

## Gaps

- No public standalone Browser control is available.
- Terminal input, arbitrary command execution, process termination, Git staging/commit, and system-wide file access are deliberately unsupported.
- ChatGPT/Desktop Project instructions cannot be read or inherited through the verified local App Server contract.
